# OKX Trading Bot v0.1 — наблюдение и безопасный Demo dry-run

Проект получает публичные данные BTC-USDT SPOT через OKX REST API V5. Команда `--check` читает последнюю цену, параметры инструмента и 100 закрытых свечей 15m. Команда `--signal` рассчитывает EMA 9/21 и показывает BUY, SELL или HOLD. Для этих команд API-ключи не нужны. `--demo-check` читает только отдельный **виртуальный** счёт OKX Demo Trading. `--dry-run` выполняет один анализ и записывает решение без исполнения. `--reconcile` сверяет доступные данные виртуального счёта с локальным журналом и Risk Manager. Функций создания, изменения, отмены ордеров и переводов в программе нет; LIVE-режим запрещён.

## Запуск в Windows PowerShell

Установите Python 3.11 или новее. Откройте PowerShell в папке `okx-trading-bot` и выполните:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe main.py --check
.\.venv\Scripts\python.exe main.py --signal
```

Если `python` в `PATH` указывает на Python 3.11+, можно также выполнить `python main.py --check` или `python main.py --signal` из этой папки. Активация виртуальной среды в PowerShell не требуется.

## Проверка виртуального Demo-счёта (этап 4A)

В OKX Demo Trading создайте **отдельный Demo API-ключ** только с правом **Read**. Не используйте ключ реального счёта и не включайте права Trade/Withdraw. Откройте локальный файл настроек командой `notepad .env` (сначала скопируйте `.env.example`, как показано выше). Укажите регион вашего Demo-аккаунта в `OKX_REGION`, установите `OKX_MODE=DEMO` и заполните `OKX_DEMO_API_KEY`, `OKX_DEMO_API_SECRET`, `OKX_DEMO_PASSPHRASE`. Эти значения читаются командой только из файла `.env` в папке проекта; переменные окружения не подменяют Demo-ключи или Demo-режим. Файл `.env` исключён из Git. Не вставляйте ключи в сообщения, тесты, README или коммиты.

```powershell
.\.venv\Scripts\python.exe main.py --demo-check
```

Команда показывает виртуальные BTC и USDT (всего и доступно), число открытых SPOT-ордеров и число последних SPOT-исполнений (до 100 записей). Идентификаторы счёта и ключи не печатаются. Если доступных виртуальных USDT нет, команда объясняет это; реальные BTC/USDT она не конвертирует, не переводит и не использует. Если `.env` отсутствует, выбран LIVE/READ_ONLY вместо DEMO, нет ключей/прав либо API вернул некорректные данные, проверка завершается ошибкой. Если OKX сообщает об ошибке времени, синхронизируйте часы Windows и повторите проверку. Интернет нужен только для этих реальных проверочных команд, офлайн-тестам он не нужен.

## Один цикл без исполнения (этап 4B.1)

После настройки **отдельного Demo-ключа** в локальном `.env` выполните из папки `okx-trading-bot`:

```powershell
.\.venv\Scripts\python.exe main.py --dry-run
```

Команда один раз получает закрытые свечи и текущую цену, вычисляет EMA 9/21, читает виртуальный Demo-счёт и записывает решение `ALLOW`, `BLOCK` или `HOLD` в `data/dry_run_journal.sqlite3`. Журнал SQLite сохраняется между запусками и исключён из Git. В нём есть ID и время UTC, свеча, сигнал, решение, причина, параметры риска и расчётные параметры гипотетической сделки. В каждой записи `executed=false`; ключи, passphrase и HTTP-заголовки не сохраняются. При повторном запуске на той же свече новая запись получает `BLOCK` и ссылку на исходное решение, поэтому повторного торгового намерения нет.

`HOLD` означает отсутствие пересечения EMA. `SELL` на этом этапе всегда даёт `BLOCK`: существующий виртуальный BTC считается внешним активом, а собственная позиция бота не подтверждена. `BUY` проходит только чистую предварительную проверку `RiskManager.preview_buy(...)`, которая читает уже существующее дневное состояние, но **не резервирует вход, не сбрасывает блокировку и не расходует дневной лимит**. Открытый ордер, устаревшая цена/свеча, ошибка Demo API или противоречивые данные дают `BLOCK`.

Текущие API-ответы ещё не подтверждают капитал на начало суток UTC, реализованный/нереализованный PnL, происхождение собственных позиций, ожидаемое проскальзывание и максимальный размер инструмента в BTC. Сверка читает ставки и фактически удержанные комиссии, но не определяет безопасную стоимость будущего исполнения. Поэтому обычный `--dry-run` **блокирует BUY**, даже если доступно 5 000 виртуальных USDT. Он не угадывает эти значения и не создаёт дневное состояние. В офлайн-тестах полное подтверждённое состояние подаётся явно, чтобы проверить расчёт `ALLOW` и отказ при недостаточном USDT. Это ограничение нужно снять проверенным источником данных в отдельном следующем этапе; оно не обходится флагом CLI.

## Сверка виртуального счёта (этап 4B.2A)

При настроенном локальном Demo `.env` выполните в Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe main.py --reconcile
```

Команда один раз читает виртуальные BTC/USDT, все открытые SPOT-ордера, до 100 последних SPOT-исполнений, их фактические комиссии и ставки maker/taker по BTC-USDT. Публичный API даёт последнюю цену и параметры инструмента (минимум, шаг, тик, поля `maxLmtSz` и `maxMktSz`). Значения максимума показываются **в единицах полей OKX** и пока не передаются Risk Manager как лимит BTC: для разных типов ордера их единицы могут отличаться. Сумма `USDT всего + BTC всего × последняя цена` является оценкой **только BTC+USDT**, а не доказательством общей стоимости счёта или себестоимости BTC.

Сверка читает SQLite-журнал только в режиме чтения и проверяет сохранённое состояние Risk Manager. Записей об исполненных ордерах бота пока нет: все решения журнала имеют `executed=false`. Поэтому существующий виртуальный 1 BTC учитывается как **внешний актив** и его продажа запрещена. История исполнений ограничена возможностями API; исполнение без связи с подтверждённой позицией, открытый ордер, отсутствие комиссии, иная SPOT-пара или неполная история дают `BLOCKED`. Текущая версия не имеет подтверждённого источника капитала на начало UTC-суток, полной истории денежных движений и себестоимости. Она **не рассчитывает вымышленный PnL и остаток дневного риска**: обычный `--reconcile` выводит `BLOCKED` с причиной даже при 1 виртуальном BTC и 5 000 виртуальных USDT. Код допускает `READY` только при явном, полном подтверждении дневной базы, PnL, денежных движений и происхождения позиций, согласованном с ранее сохранённым состоянием; CLI такого подтверждения не создаёт. `--reconcile` никогда не вызывает `initialize_day`, не записывает журнал и не меняет лимиты.

Если команда возвращает код 1 и `BLOCKED`, это ожидаемая безопасная остановка до следующего этапа подтверждения данных. Реальный BTC, LIVE API и переводы не используются. Не копируйте в сообщения, тесты или Git ключи и файл `.env`.

Приватные GET-запросы используют официальную схему подписи OKX V5: Base64(HMAC-SHA256(secret, `timestamp + GET + requestPathWithQuery`)), время UTC ISO 8601 с миллисекундами, заголовки `OK-ACCESS-*` и обязательный `x-simulated-trading: 1`. Используются только `GET /api/v5/account/balance?ccy=BTC,USDT`, `GET /api/v5/trade/orders-pending?instType=SPOT`, `GET /api/v5/trade/fills-history?instType=SPOT` и для сверки `GET /api/v5/account/trade-fee?instType=SPOT&instId=BTC-USDT`. Список открытых ордеров читается страницами; история исполнений ограничена последними 100 записями и сроком хранения OKX. Официальная документация: https://www.okx.com/docs-v5/en/ (разделы REST Authentication, Get balance, Get order list, Get transaction details (last 3 months), Get fee rates, Demo trading).

В `.env` укажите `OKX_REGION` согласно региону вашего аккаунта: `global` использует `https://www.okx.com`, `eea` — `https://eea.okx.com`, `us` — `https://us.okx.com`. Адрес выбирается только по региону; программа не переключается на другой домен при ошибке доступа. Сверьте регион с документацией и настройками своего аккаунта OKX. Публичные методы: `GET /api/v5/market/candles`, `GET /api/v5/market/ticker`, `GET /api/v5/public/instruments` (документация: https://www.okx.com/docs-v5/en/).

Для получения 100 *закрытых* свечей программа запрашивает 101 последнюю запись и отбрасывает свечи с `confirm=0`. Если закрытых свечей меньше 100 или ответ некорректен, команда завершается ошибкой. Сетевые запросы ограничены тайм-аутом и тремя попытками по умолчанию.

EMA начинается со среднего арифметического первых 9 или 21 цен закрытия, затем обновляется на каждой следующей свече. Для сигнала сравниваются значения EMA на двух последних закрытых свечах: пересечение снизу вверх даёт BUY, сверху вниз — SELL, отсутствие пересечения — HOLD. Нужны минимум 22 подтверждённые свечи по порядку от старой к новой с интервалом 15 минут. При пропуске, неверном порядке или некорректной цене команда сообщает ошибку. Сигнал служит только для наблюдения и не отправляет ордер.

## Risk Manager (этап 3, без торговли)

`bot/risk_manager.py` проверяет только предполагаемую покупку BTC-USDT SPOT и возвращает `ALLOW` или `DENY` с причиной, количеством BTC, ценой входа, стопом, тейком, расчётным риском и расходом USDT. Он не подключается к OKX и не отправляет ордера. Команды `--check` и `--signal` работают как прежде; команды для торговли нет.

Правила по умолчанию: риск на вход — 0,5% текущего капитала, стоп — 1% ниже цены входа, тейк — 2% выше, дневной предел убытка — 2% **зафиксированного капитала на начало суток UTC**, максимум одна открытая позиция и пять новых входов за сутки. Усреднение запрещено. При расчёте дневного убытка складываются отрицательные реализованный и нереализованный PnL; прибыль в одном компоненте не скрывает убыток в другом. Остаток дневного лимита дополнительно ограничивает риск нового входа.

Модулю обязательно нужны свежий полный снимок счёта, доступный баланс USDT, параметры BTC-USDT от OKX (`min_size`, `lot_size`, `tick_size`, максимальный размер в **BTC**, состояние инструмента), а также реальные ставки комиссий и оценки проскальзывания для входа и выхода по стопу. Эти ставки не угадываются. Неизвестные, устаревшие или противоречивые данные дают `DENY`. Значение максимального размера нужно передавать в единицах BTC после проверки единиц исходного поля OKX.

Перед первой проверкой суток вызывается `RiskManager.initialize_day(...)` с проверенным капиталом на начало дня. Модуль сохраняет дневной счётчик, резервирование входа и блокировку потерь в `data/risk_state.json`; файл исключён из Git. Повторная инициализация в те же сутки не снимает блокировку, а после перезапуска модуль читает сохранённое состояние. Новый день UTC требует явной инициализации с новым проверенным капиталом. Если состояние отсутствует, повреждено или занято, проверка возвращает `DENY`. `ALLOW` лишь резервирует один вход; повторный вызов вернёт `DENY`. Резервирование снимается только методом `reconcile_confirmed_entry(...)` после подтверждения входа в достоверной истории счёта. Неподтверждённое резервирование остаётся заблокированным до следующего дня UTC.

Пример расчёта (условные числа, не котировка): капитал 10 000 USDT даёт бюджет риска 50 USDT. При входе 100 000 USDT за BTC, стопе 99 000, тейке 102 000, комиссии 0,1% и ожидаемом проскальзывании 0,1% на каждой стороне стоимость входа за 1 BTC составит 100 200,1 USDT, а поступление по стопу — 98 802,099 USDT. Риск на 1 BTC равен 1 398,001 USDT. При шаге количества 0,0000001 BTC размер округляется вниз до **0,0357653 BTC**: расчётный убыток 49,9999251653 USDT, расход 3 583,68663653 USDT. Если доступно меньше этого расхода, размер уменьшается по балансу. Если даже минимальный лот не укладывается в риск или баланс, результат — `DENY`.

Пример дневной блокировки: при капитале на начало UTC-суток 10 000 USDT предел равен 200 USDT. Реализованный убыток 150 USDT и нереализованный убыток 50 USDT достигают предела. Новая покупка запрещена на оставшуюся часть суток, в том числе после перезапуска программы или временного восстановления PnL.

## Офлайн-тесты

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Тесты подменяют ответы API и не используют интернет. `OKX_MODE=LIVE` запрещён. Все приватные вызовы требуют режим `DEMO` и заголовок `x-simulated-trading: 1`; торговые и переводные API отсутствуют. `.env`, виртуальная среда и файлы состояния исключены из Git.
