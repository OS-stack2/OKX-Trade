# OKX Trading Bot v0.1 — наблюдение и безопасный Demo dry-run

Проект получает публичные данные BTC-USDT SPOT через OKX REST API V5. Команда `--check` читает последнюю цену, параметры инструмента и 100 закрытых свечей 15m. Команда `--signal` рассчитывает EMA 9/21 и показывает BUY, SELL или HOLD. Для этих команд API-ключи не нужны. `--demo-check` читает только отдельный **виртуальный** счёт OKX Demo Trading. `--dry-run` выполняет один анализ и записывает решение без исполнения. `--reconcile` сверяет доступные данные виртуального счёта с локальным журналом и Risk Manager. `--order-preview` показывает заблокированный предварительный план покупки. Функций создания, изменения, отмены ордеров и переводов в программе нет; LIVE-режим запрещён.

## Запуск в Windows PowerShell

Установите Python 3.11 или новее. Откройте PowerShell в папке `okx-trading-bot` и выполните:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe main.py --check
.\.venv\Scripts\python.exe main.py --signal
```

Если `python` в `PATH` указывает на Python 3.11+, можно также выполнить `python main.py --check` или `python main.py --signal` из этой папки. Активация виртуальной среды в PowerShell не требуется.

## Проверка виртуального Demo-счёта (этап 4A)

В OKX Demo Trading создайте **отдельный Demo API-ключ** только с правом **Read**. Не используйте ключ реального счёта и не включайте права Trade/Withdraw. Откройте локальный файл настроек командой `notepad .env` (сначала скопируйте `.env.example`, как показано выше). Укажите регион вашего Demo-аккаунта в `OKX_REGION`, установите `OKX_MODE=DEMO` и заполните `OKX_DEMO_API_KEY`, `OKX_DEMO_API_SECRET`, `OKX_DEMO_PASSPHRASE`. Эти значения читаются командой только из файла `.env` в папке проекта; переменные окружения не подменяют Demo-ключи или Demo-режим. Файл `.env` исключён из Git. Не вставляйте ключи в сообщения, тесты, README или коммиты.

```powershell
.\.venv\Scripts\python.exe main.py --demo-check
```

Команда показывает виртуальные BTC и USDT (всего и доступно), число открытых SPOT-ордеров и число последних SPOT-исполнений (до 100 записей). Идентификаторы счёта и ключи не печатаются. Если доступных виртуальных USDT нет, команда объясняет это; реальные BTC/USDT она не конвертирует, не переводит и не использует. Если `.env` отсутствует, выбран LIVE/READ_ONLY вместо DEMO, нет ключей/прав либо API вернул некорректные данные, проверка завершается ошибкой. Если OKX сообщает об ошибке времени, синхронизируйте часы Windows и повторите проверку. Интернет нужен только для этих реальных проверочных команд, офлайн-тестам он не нужен.

## Один цикл без исполнения (этап 4B.1)

После настройки **отдельного Demo-ключа** в локальном `.env` выполните из папки `okx-trading-bot`:

```powershell
.\.venv\Scripts\python.exe main.py --dry-run
```

Команда один раз получает закрытые свечи и текущую цену, вычисляет EMA 9/21, читает виртуальный Demo-счёт и записывает решение `ALLOW`, `BLOCK` или `HOLD` в `data/dry_run_journal.sqlite3`. Журнал SQLite сохраняется между запусками и исключён из Git. В нём есть ID и время UTC, свеча, сигнал, решение, причина, параметры риска и расчётные параметры гипотетической сделки. В каждой записи `executed=false`; ключи, passphrase и HTTP-заголовки не сохраняются. При повторном запуске на той же свече новая запись получает `BLOCK` и ссылку на исходное решение, поэтому повторного торгового намерения нет.

`HOLD` означает отсутствие пересечения EMA. `SELL` на этом этапе всегда даёт `BLOCK`: существующий виртуальный BTC считается внешним активом, а собственная позиция бота не подтверждена. `BUY` проходит только чистую предварительную проверку `RiskManager.preview_buy(...)`, которая читает уже существующее дневное состояние, но **не резервирует вход, не сбрасывает блокировку и не расходует дневной лимит**. Открытый ордер, устаревшая цена/свеча, ошибка Demo API или противоречивые данные дают `BLOCK`.

Текущие API-ответы ещё не подтверждают капитал на начало суток UTC, реализованный/нереализованный PnL, происхождение собственных позиций, ожидаемое проскальзывание и максимальный размер инструмента в BTC. Сверка читает ставки и фактически удержанные комиссии, но не определяет безопасную стоимость будущего исполнения. Поэтому обычный `--dry-run` **блокирует BUY**, даже если доступно 5 000 виртуальных USDT. Он не угадывает эти значения и не создаёт дневное состояние. В офлайн-тестах полное подтверждённое состояние подаётся явно, чтобы проверить расчёт `ALLOW` и отказ при недостаточном USDT. Это ограничение нужно снять проверенным источником данных в отдельном следующем этапе; оно не обходится флагом CLI.

## Сверка виртуального счёта (этап 4B.2A)

При настроенном локальном Demo `.env` выполните в Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe main.py --reconcile
```

Команда один раз читает виртуальные BTC/USDT, все открытые SPOT-ордера, до 100 последних SPOT-исполнений, их фактические комиссии и ставки maker/taker по BTC-USDT. Публичный API даёт последнюю цену и параметры инструмента (минимум, шаг, тик, поля `maxLmtSz` и `maxMktSz`). Значения максимума показываются **в единицах полей OKX** и пока не передаются Risk Manager как лимит BTC: для разных типов ордера их единицы могут отличаться. Сумма `USDT всего + BTC всего × последняя цена` является оценкой **только BTC+USDT**, а не доказательством общей стоимости счёта или себестоимости BTC.

Сверка читает SQLite-журнал только в режиме чтения и проверяет сохранённое состояние Risk Manager. Записей об исполненных ордерах бота пока нет: все решения журнала имеют `executed=false`. Поэтому существующий виртуальный 1 BTC учитывается как **внешний актив** и его продажа запрещена. История исполнений ограничена возможностями API; исполнение без связи с подтверждённой позицией, открытый ордер, отсутствие комиссии, иная SPOT-пара или неполная история дают `BLOCKED`. До явного подтверждения бюджета `--reconcile` выводит `BLOCKED`: капитал стратегии и её дневная база не установлены. После подтверждения команда может вывести `READY`, только если баланс не менялся, исполнений и открытых ордеров по-прежнему нет, а состояние Risk Manager совпадает с сохранённой базой. Тогда PnL **бота без позиций и исполнений** равен нулю; изменение цены внешнего BTC не входит в него. При любом необъяснимом движении баланса PnL снова становится неизвестным и результат — `BLOCKED`. `--reconcile` никогда не вызывает `initialize_day`, не записывает журнал и не меняет лимиты.

Если команда возвращает код 1 и `BLOCKED`, это ожидаемая безопасная остановка до следующего этапа подтверждения данных. Реальный BTC, LIVE API и переводы не используются. Не копируйте в сообщения, тесты или Git ключи и файл `.env`.

## Однократный бюджет стратегии (этап 4B.2A.1)

Владелец выделил **5 000 виртуальных USDT** из уже доступного баланса Demo для BTC-USDT SPOT. Это отдельная стартовая база стратегии; внешний 1 BTC не входит в неё. Сначала посмотрите свежую проверку:

```powershell
.\.venv\Scripts\python.exe main.py --budget-preview
```

Просмотр ничего не записывает. Он требует локальный Demo Read-only ключ, целый SQLite-журнал решений, точно 1 свободный внешний BTC, не менее 5 000 свободных виртуальных USDT без скрытого резерва, ноль открытых SPOT-ордеров и исполнений в полной доступной истории, действующие параметры BTC-USDT и ставки комиссий. Проверяется, что минимальный лот вместе с taker-комиссией укладывается в бюджет; эта проверка **не** разрешает будущий ордер и не подменяет расчёт проскальзывания. Если проверка готова, она печатает точную команду с фразой `CONFIRM DEMO BTC-USDT 5000 USDT` и коротким токеном. Только личный запуск этой команды после просмотра подтверждает выделение. Токен привязан к снимку балансов, комиссиям, ограничениям и журналу, действует в текущем пятиминутном окне UTC; при изменении данных нужно снова выполнить `--budget-preview`.

Подтверждение повторно читает OKX и SQLite, затем **один раз** записывает базу в `data/dry_run_journal.sqlite3` и инициализирует `data/risk_state.json` на текущие UTC-сутки. Сохраняются UTC-время, 5 000 USDT капитала стратегии, наблюдавшиеся виртуальные балансы BTC/USDT, оценка BTC+USDT, ставки комиссий и происхождение бюджета: решение владельца выделить уже существующие Demo USDT. Для первого дня стратегия начинается **в момент подтверждения**, а не задним числом в полночь UTC; её лимит действует до следующей границы UTC-суток. Это не подтверждение экономического происхождения всех средств на бирже; бот не делал пополнение или перевод. Оба файла исключены из Git. Повторная команда не перезаписывает базу, не снимает дневную блокировку и не обнуляет потери. Если запись одного из файлов не завершилась, состояние остаётся заблокированным до ручной сверки; повторное подтверждение не служит способом сброса.

При неизменном виртуальном счёте `--reconcile` показывает капитал стратегии 5 000 USDT, нулевой подтверждённый PnL бота, предел риска **25 USDT на сделку** и **100 USDT за текущие UTC-сутки**. Эти числа не включают внешний BTC или его изменение цены. Максимум одна позиция, пять новых входов за день, SL 1% и TP 2% остаются настройками Risk Manager. Если после подтверждения баланс, ордера, исполнения или журнал расходятся, состояние — `BLOCKED`, PnL не угадывается. На следующий день UTC новый лимит **не создаётся автоматически**, а повторное подтверждение стартового бюджета запрещено; до отдельной проверенной процедуры нового дня система блокируется. `--dry-run` по-прежнему не исполняет ордера и не превращает новый бюджет в торговое разрешение: для гипотетического BUY ему всё ещё нужны полные данные по проскальзыванию и лимиту количества BTC.

Приватные GET-запросы используют официальную схему подписи OKX V5: Base64(HMAC-SHA256(secret, `timestamp + GET + requestPathWithQuery`)), время UTC ISO 8601 с миллисекундами, заголовки `OK-ACCESS-*` и обязательный `x-simulated-trading: 1`. Используются только `GET /api/v5/account/balance?ccy=BTC,USDT`, `GET /api/v5/trade/orders-pending?instType=SPOT`, `GET /api/v5/trade/fills-history?instType=SPOT` и для сверки `GET /api/v5/account/trade-fee?instType=SPOT&instId=BTC-USDT`. Список открытых ордеров читается страницами; история исполнений ограничена последними 100 записями и сроком хранения OKX. Официальная документация: https://www.okx.com/docs-v5/en/ (разделы REST Authentication, Get balance, Get order list, Get transaction details (last 3 months), Get fee rates, Demo trading).

В `.env` укажите `OKX_REGION` согласно региону вашего аккаунта: `global` использует `https://www.okx.com`, `eea` — `https://eea.okx.com`, `us` — `https://us.okx.com`. Адрес выбирается только по региону; программа не переключается на другой домен при ошибке доступа. Сверьте регион с документацией и настройками своего аккаунта OKX. Публичные методы: `GET /api/v5/market/candles`, `GET /api/v5/market/ticker`, `GET /api/v5/public/instruments` (документация: https://www.okx.com/docs-v5/en/).

Для получения 100 *закрытых* свечей программа запрашивает 101 последнюю запись и отбрасывает свечи с `confirm=0`. Если закрытых свечей меньше 100 или ответ некорректен, команда завершается ошибкой. Сетевые запросы ограничены тайм-аутом и тремя попытками по умолчанию.

EMA начинается со среднего арифметического первых 9 или 21 цен закрытия, затем обновляется на каждой следующей свече. Для сигнала сравниваются значения EMA на двух последних закрытых свечах: пересечение снизу вверх даёт BUY, сверху вниз — SELL, отсутствие пересечения — HOLD. Нужны минимум 22 подтверждённые свечи по порядку от старой к новой с интервалом 15 минут. При пропуске, неверном порядке или некорректной цене команда сообщает ошибку. Сигнал служит только для наблюдения и не отправляет ордер.

## Risk Manager (этап 3, без торговли)

`bot/risk_manager.py` проверяет только предполагаемую покупку BTC-USDT SPOT и возвращает `ALLOW` или `DENY` с причиной, количеством BTC, ценой входа, стопом, тейком, расчётным риском и расходом USDT. Он не подключается к OKX и не отправляет ордера. Команды `--check` и `--signal` работают как прежде; команды для торговли нет.

Правила по умолчанию: риск на вход — 0,5% текущего капитала, стоп — 1% ниже цены входа, тейк — 2% выше, дневной предел убытка — 2% **зафиксированного капитала на начало суток UTC**, максимум одна открытая позиция и пять новых входов за сутки. Усреднение запрещено. При расчёте дневного убытка складываются отрицательные реализованный и нереализованный PnL; прибыль в одном компоненте не скрывает убыток в другом. Остаток дневного лимита дополнительно ограничивает риск нового входа.

Модулю обязательно нужны свежий полный снимок счёта, доступный баланс USDT, параметры BTC-USDT от OKX (`min_size`, `lot_size`, `tick_size`, максимальный размер в **BTC**, состояние инструмента), а также реальные ставки комиссий и оценки проскальзывания для входа и выхода по стопу. Эти ставки не угадываются. Неизвестные, устаревшие или противоречивые данные дают `DENY`. Значение максимального размера нужно передавать в единицах BTC после проверки единиц исходного поля OKX.

Перед первой проверкой суток вызывается `RiskManager.initialize_day(...)` с проверенным капиталом на начало дня. Модуль сохраняет дневной счётчик, резервирование входа и блокировку потерь в `data/risk_state.json`; файл исключён из Git. Повторная инициализация в те же сутки не снимает блокировку, а после перезапуска модуль читает сохранённое состояние. Новый день UTC требует явной инициализации с новым проверенным капиталом. Если состояние отсутствует, повреждено или занято, проверка возвращает `DENY`. `ALLOW` лишь резервирует один вход; повторный вызов вернёт `DENY`. Резервирование снимается только методом `reconcile_confirmed_entry(...)` после подтверждения входа в достоверной истории счёта. Неподтверждённое резервирование остаётся заблокированным до следующего дня UTC.

Пример расчёта (условные числа, не котировка): капитал 10 000 USDT даёт бюджет риска 50 USDT. При входе 100 000 USDT за BTC, стопе 99 000, тейке 102 000, комиссии 0,1% и ожидаемом проскальзывании 0,1% на каждой стороне стоимость входа за 1 BTC составит 100 200,1 USDT, а поступление по стопу — 98 802,099 USDT. Риск на 1 BTC равен 1 398,001 USDT. При шаге количества 0,0000001 BTC размер округляется вниз до **0,0357653 BTC**: расчётный убыток 49,9999251653 USDT, расход 3 583,68663653 USDT. Если доступно меньше этого расхода, размер уменьшается по балансу. Если даже минимальный лот не укладывается в риск или баланс, результат — `DENY`.

Пример дневной блокировки: при капитале на начало UTC-суток 10 000 USDT предел равен 200 USDT. Реализованный убыток 150 USDT и нереализованный убыток 50 USDT достигают предела. Новая покупка запрещена на оставшуюся часть суток, в том числе после перезапуска программы или временного восстановления PnL.

## Подготовка исполнителя без отправки (этап 4B.2B-1)

В Windows PowerShell проверьте локальное состояние:

```powershell
.\.venv\Scripts\python.exe main.py --execution-check
```

Команда читает только SQLite-журнал в `data/dry_run_journal.sqlite3`; интернет и API-ключи ей не нужны. `CLEAR` означает лишь отсутствие локальных незавершённых намерений. Это **не разрешение на торговлю**. `BLOCKED` и код выхода 1 означают, что сохранено намерение, исполнение, неопределённое состояние либо аварийная остановка. Состояния: `PLANNED`, `VALIDATED`, `SUBMITTING`, `ACKNOWLEDGED`, `PARTIALLY_FILLED`, `FILLED`, `REJECTED`, `UNKNOWN`, `HALTED`.

`bot/execution_engine.py` — локальная модель будущего цикла. Она сохраняет уникальный `clientOrderId` и рассчитанные параметры в том же SQLite до возможной будущей отправки. Повторный план для той же свечи запрещён, после перезапуска `SUBMITTING` и `UNKNOWN` остаются заблокированы. Таймаут и неоднозначный ответ переводят состояние в `UNKNOWN`: повторной отправки нет. Частичные исполнения и комиссии можно учитывать только из проверенных сведений биржи; неподдающийся защите размер или противоречие вызывает сохраняемую `HALTED`. Стоп на 1% и тейк на 2% округляются и проверяются по шагам BTC-USDT, но **защитные ордера не создаются**. Восстановление аварийной остановки требует ручной сверки конкретного идентификатора с Demo-счётом; текущая CLI не предоставляет способа обхода блокировки.

В этом этапе нет CLI-команды для планирования или отправки, сетевого клиента для исполнения, POST-запросов или изменения ключей API. Модель принимает только гипотетический BUY после свежего `READY`, подтверждённого бюджета 5 000 виртуальных USDT и повторного подтверждения Risk Manager. Внешний 1 BTC не входит в капитал стратегии и продаваться не может. Для реального планирования всё ещё нужны проверенные единицы максимального размера в BTC и оценка проскальзывания; текущая команда `--dry-run` не подменяет их. Суточная база и лимиты Risk Manager этим этапом не меняются.

Старые команды остаются доступны: `--check`, `--signal`, `--demo-check`, `--dry-run`, `--reconcile`, `--budget-preview`. Дневные лимиты 0,5% на сделку, 2% убытка, одна позиция, пять входов, стоп 1% и тейк 2% действуют как прежде.

## Офлайн-симуляция защиты (этап 4B.2B-2D)

Из папки `okx-trading-bot` в Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe main.py --protection-simulate
.\.venv\Scripts\python.exe main.py --protection-simulate --sim-price-path "80000,79200,78400"
```

Цены разделяются запятыми; допускается от 1 до 20 положительных цен в USDT за BTC. По умолчанию используется путь `80000,79200,78400`. Команда создаёт **только временную SQLite** в системной папке Temp, записывает туда учебные события, закрывает каждое соединение и удаляет временную папку после отчёта. Путь к рабочей `data/dry_run_journal.sqlite3` симулятор отвергает. Команда не читает `.env`, не подключается к OKX, не вызывает Risk Manager и не меняет подтверждённую базу 5 000 виртуальных USDT.

В модели взят **пример**, а не параметры вашего аккаунта: BUY 0,02 BTC по 80 000 USDT, `minSz=0.00001`, `lotSz=0.00000001`, `tickSz=0.1`, условный максимум LIMIT 1 BTC. Стоп 1% округляется вниз до 79 200 USDT, тейк 2% вверх до 81 600 USDT. BUY-комиссия в примере составляет 0,1% BTC: после полного входа бот владеет 0,01998 BTC. SL и TP планируются на этот **чистый** объём с округлением вниз до `lotSz`. Если остаток после округления нельзя защитить, он остаётся незащищённым и блокирует исполнение. Две ноги одного синтетического OCO резервируют BTC только один раз; повторная группа или исполнение второй ноги после первой не может списать внешний 1 BTC.

Отчёт содержит десять учебных сценариев: полный BUY и мгновенное подтверждение OCO; полный цикл до закрытия по TP с учебным PnL; частичный BUY с задержкой SL и новой частью; отмену остатка BUY; отказ BUY; таймаут; отказ защиты; частичный fill защитного ордера; дублирующую защиту; обрыв и перезапуск. Состояние восстанавливается повторным чтением временного SQLite-журнала. `HALTED` сохраняется после позднего подтверждения SL и после перезапуска: симуляция не умеет снять блокировку. Интервал незащищённости считается с первой подтверждённой покупки до подтверждения защиты или закрытия позиции; при неизвестном результате таймаута длительность и потери выводятся как **неизвестные**, а не ноль. Значение `0 с` при событиях с одинаковой секундой не доказывает атомарность реального OKX API. Учебный реализованный PnL рассчитывается только после полного, внутренне непротиворечивого закрытия и включает комиссии BUY/SELL; при частичном или неизвестном выходе итоговый PnL остаётся неизвестным.

Для каждой заданной цены программа показывает **условный возможный убыток** по позиции бота: стоимость BUY с фактической учебной комиссией минус уже полученные учебные поступления от защитного SELL и условная стоимость оставшегося BTC при выходе по этой цене с оценкой комиссии 0,1% и проскальзывания 0,1%. Это не верхняя граница: ценовой разрыв, неполное исполнение SL или иные издержки могут увеличить потери. Внешний 1 BTC полностью исключён из расчёта. Любой результат остаётся `BLOCK`, код выхода команды — **1**; успешный учебный OCO не подтверждает поддержку attached TP/SL в вашем регионе и не разрешает реальную Demo-торговлю.

## Аварийная сверка позиции (этап 4B.2B-2E)

Из папки `okx-trading-bot` в Windows PowerShell, с отдельным **Demo Read-only** ключом в локальном `.env`:

```powershell
.\.venv\Scripts\python.exe main.py --recovery-check
```

Код выхода **1** и `BLOCKED` ожидаемы: эта команда не разрешает торговлю. Если в SQLite есть BUY-намерение, `bot/recovery_manager.py` сначала **устойчиво записывает `HALTED`**, затем читает виртуальные BTC/USDT, все открытые SPOT-ордера, pending conditional/OCO Algo-ордера, точный BUY по `clientOrderId`, его fills и комиссии по `ordId`, а также сохранённые Algo ID. Сверяются суммы fills, комиссии, чистый BTC бота, исходный внешний 1 BTC, виртуальный USDT и чужие ордера. Повторный запуск не дублирует fills; подтверждённый по GET fill записывается в SQLite один раз. Состояние переживает перезапуск. При таймауте или неполной истории фактический объём выводится как неизвестный. Никакой торговый запрос не отправляется.

Даже найденные по ID и размеру Algo GET не доказывают их привязку к BUY, атомарность появления SL на каждой частично купленной порции и взаимоисключение SL/TP. Поэтому **подтверждённое покрытие в этой аварийной команде равно нулю**, купленный BTC считается незащищённым, а `HALTED` не снимается автоматически. Если после восстановления связи GET прошли, команда сообщает об этом, но оставляет блокировку. Внешний 1 BTC из подтверждённого бюджета никогда не относится к позиции бота, не резервируется и не продаётся. Бюджет 5 000 USDT, дневная база и лимиты Risk Manager командой не изменяются. При отсутствии собственной позиции команда не создаёт новое торговое намерение.

Для необязательных уведомлений владельцу добавьте **только в локальный `.env`** значения `OKX_TELEGRAM_BOT_TOKEN` и `OKX_TELEGRAM_CHAT_ID`; шаблон есть в `.env.example`. Бот Telegram должен иметь доступ к чату. Сообщения о `HALTED`, незащищённом BTC, расхождении и восстановлении связи содержат только общую диагностику. Токен не печатается и не записывается в SQLite. Уведомление отправляется **после** записи аварийного состояния; ошибка Telegram не отменяет остановку. Это единственный POST нового модуля, направленный в Telegram `sendMessage`; к OKX по-прежнему идут только GET. Не вставляйте токен или chat ID в Git и сообщения. При ненастроенном Telegram отчёт пишет «не настроен», а защита работает как обычно.

После `BLOCKED` проверьте виртуальный Demo-счёт вручную: статус конкретного BUY, все fills и комиссии, чистый BTC бота, открытые ордера и идентификаторы защиты. До отдельной доказанной процедуры `HALTED` и запрет новых сделок сохраняются. Команда не продаёт даже незащищённую позицию и не использует реальный BTC. Для проверки без сети:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe main.py --execution-check
```

## OKX Watchdog для Ubuntu 24.04 (этап 4B.2B-2G)

`--watchdog-once` выполняет **одну** проверку и завершает процесс. Она читает публичный BTC-USDT ticker и отдельные Demo GET баланса BTC/USDT, всех открытых SPOT-ордеров и ожидающих conditional/OCO Algo-ордеров. Путь к рабочей Windows SQLite команда не открывает: её снимки, состояние связи и отметки об уведомлениях находятся только в отдельном `watchdog.sqlite3`. При отсутствии `OKX_WATCHDOG_STATE_PATH` локальный путь — `watchdog_data/watchdog.sqlite3`, исключённый из Git; для systemd путь явно задаётся как `/var/lib/okx-watchdog/watchdog.sqlite3`.

Отчёт `OBSERVED_UNVERIFIED` означает лишь, что GET завершились и снимок сохранён. Даже при пустых списках ордеров Watchdog **не знает**, какой BTC принадлежит стратегии, и не подтверждает наличие SL: `CLEAR` и разрешение торговли он никогда не выдаёт. Изменение BTC/USDT или ордеров, неизвестные открытые заявки, Algo-ордера и необъяснимое резервирование отмечаются как `SUSPICIOUS`; ошибка или устаревший ticker — как `API_UNAVAILABLE`. При недоступном отдельном журнале результат `JOURNAL_ERROR`. Исходный 1 BTC не считается позицией бота и не используется для операций. Код выхода `0` возможен только при сохранённом обычном наблюдении без ошибки уведомления; остальные исходы дают `1`.

Предыдущий успешный снимок переживает таймауты и перезапуски. Telegram получает одно уведомление на начало сбоя, одно при восстановлении связи и уведомление при новом изменении или подозрительном снимке. Повторная одинаковая проверка не отправляет дубликат. Попытка уведомления записывается **до** вызова Telegram; неоднозначный тайм-аут не вызывает повторную отправку того же события. Это ограничивает дубли, но Telegram не предоставляет гарантии «ровно один раз»: при обрыве после записи попытки сообщение может не дойти. Проверяйте `journalctl`, если сервис сообщает об ошибке доставки. SQLite хранит максимум 576 наблюдений (около двух суток) и 200 отметок уведомлений; исходные ключи, HTTP-заголовки и идентификаторы ордеров в журнал не записываются (для сравнения используются хеши).

Ниже — **инструкция для будущей отдельной установки**. В этом этапе на сервере ничего не устанавливалось и существующие сервисы, SSH и сетевые настройки не менялись. Команды выполняйте на Ubuntu 24.04 только для нового `/opt/okx-watchdog` и новых файлов `okx-watchdog.service`/`.timer`:

1. Убедитесь, что доступны `git`, Python 3.11+ и модуль `venv`: `git --version`, `python3 --version`, `python3 -m venv --help`. Проверьте часы командой `timedatectl status`. Если какого-то пакета нет, установите только недостающий после проверки сервера.
2. Убедитесь, что отдельный пользователь `okx-watchdog`, каталог `/opt/okx-watchdog` и одноимённые unit-файлы ещё не существуют: `id okx-watchdog` должен сообщить, что пользователя нет; затем выполните `test ! -e /opt/okx-watchdog`, `test ! -e /etc/systemd/system/okx-watchdog.service`, `test ! -e /etc/systemd/system/okx-watchdog.timer`. Если что-то существует, остановитесь и проверьте вручную; не перезаписывайте файлы.
3. Создайте отдельного пользователя и новую копию кода:

   ```bash
   sudo useradd --system --home /var/lib/okx-watchdog --no-create-home --shell /usr/sbin/nologin okx-watchdog
   sudo git clone --branch main --depth 1 https://github.com/OS-stack2/OKX-Trade.git /opt/okx-watchdog
   sudo python3 -m venv /opt/okx-watchdog/okx-trading-bot/.venv
   ```

4. Создайте **новый** `.env` с правами только для пользователя Watchdog. Перед `install` убедитесь, что файла ещё нет; не копируйте Windows `.env` или рабочую SQLite:

   ```bash
   sudo test ! -e /opt/okx-watchdog/okx-trading-bot/.env
   sudo install -o okx-watchdog -g okx-watchdog -m 600 /dev/null /opt/okx-watchdog/okx-trading-bot/.env
   sudoedit /opt/okx-watchdog/okx-trading-bot/.env
   sudo stat -c '%U %G %a' /opt/okx-watchdog/okx-trading-bot/.env
   ```

   В `.env` укажите `OKX_MODE=DEMO`, правильный для **этого Demo-аккаунта** `OKX_REGION`, отдельный Demo API key/secret/passphrase с разрешением **Read only**, Telegram token/chat ID и `OKX_WATCHDOG_STATE_PATH=/var/lib/okx-watchdog/watchdog.sqlite3`. Для короткого цикла можно установить `OKX_TIMEOUT_SECONDS=3` и `OKX_MAX_ATTEMPTS=2`. Watchdog откажется запускаться на Ubuntu, если `.env` доступен группе или другим пользователям либо является символической ссылкой. Не включайте Trade/Withdraw, LIVE и реальные ключи. Значения секретов не передавайте в аргументах команд или сообщения. Программа не может по GET доказать набор прав выданного ключа: убедитесь в **Read only** в настройках OKX.
5. Проверьте офлайн-тесты и установите **только новые** unit-файлы из `deploy/systemd`:

   ```bash
   cd /opt/okx-watchdog/okx-trading-bot
   ./.venv/bin/python -m unittest discover -s tests -q
   sudo install -o root -g root -m 644 deploy/systemd/okx-watchdog.service /etc/systemd/system/okx-watchdog.service
   sudo install -o root -g root -m 644 deploy/systemd/okx-watchdog.timer /etc/systemd/system/okx-watchdog.timer
   sudo systemd-analyze verify /etc/systemd/system/okx-watchdog.service /etc/systemd/system/okx-watchdog.timer
   sudo systemctl daemon-reload
   ```

6. Запустите один пробный цикл, затем включите только новый таймер:

   ```bash
   sudo systemctl start okx-watchdog.service
   sudo journalctl -u okx-watchdog.service -n 30 --no-pager
   sudo systemctl enable --now okx-watchdog.timer
   systemctl list-timers --all okx-watchdog.timer
   ```

   `SUSPICIOUS`/`API_UNAVAILABLE` дают ненулевой код, поэтому пробный `systemctl start` может показать failed; сначала прочитайте отчёт. Таймер запускает один процесс каждые пять минут, а не бесконечный цикл. Для остановки **только этого** мониторинга: `sudo systemctl disable --now okx-watchdog.timer`.

Unit работает под непривилегированным пользователем, с `UMask=0077`, приватным `StateDirectory` (`0700`), правами файла SQLite `0600`, read-only кодом, лимитами памяти/CPU/задач/времени и ограничением частоты записей в systemd journal. Он не меняет firewall, DNS, SSH или другие службы. Нужен исходящий HTTPS к региональному домену OKX и Telegram; при недоступности региона другой домен автоматически не выбирается. Помимо Telegram `sendMessage`, Watchdog использует только GET; торговых POST, BUY/SELL и переводов нет.

Существующий бюджет 5 000 виртуальных USDT, риск 0,5%/2%, стоп 1%, тейк 2% и база UTC не менялись. Торговых POST, переводов, LIVE и продажи внешнего BTC нет.

## Health Monitor для установленного Ubuntu Watchdog (этап 4B.2B-2H)

`python main.py --health-once` делает один **офлайн**-цикл: читает отдельный `watchdog.sqlite3` через SQLite `mode=ro`, проверяет последний успешный GET и завершает процесс. Запросов к OKX нет. Порог просрочки по умолчанию — **15 минут**; при необходимости укажите в локальном `.env` `OKX_HEALTH_STALE_MINUTES=15` (целое число 1–1440). Нужны существующие `OKX_MODE=DEMO` и `OKX_WATCHDOG_STATE_PATH=/var/lib/okx-watchdog/watchdog.sqlite3`. Собственное состояние и дедупликация сохраняются **рядом**, в `/var/lib/okx-watchdog/health.sqlite3` с правами `0600`. Рабочая торговая SQLite не читается и не меняется.

`HEALTHY` означает лишь свежий успешный GET Watchdog; это **не** подтверждение принадлежности BTC, SL или права на торговлю. `STALE` — успешный GET старше порога либо пропущены запуски. `API_UNAVAILABLE` — последний записанный цикл Watchdog завершился ошибкой GET, даже если предыдущий GET свежий. `UNKNOWN` — данных нет, SQLite/время противоречивы, часы переведены назад или конфигурация недоступна. Только `HEALTHY` возвращает код `0`; остальные состояния — `1`. Telegram извещает о просрочке, ошибке API и восстановлении **после нового успешного GET**. Попытка фиксируется до отправки, поэтому неоднозначный таймаут не повторяется после перезапуска. Ошибка Telegram не откатывает состояние. При ошибке собственной SQLite результат — `UNKNOWN` без отправки. Единственный возможный POST — Telegram `sendMessage`, не OKX. `HALTED`, риск и бюджет монитор не открывает.

На **уже работающем** Ubuntu 24.04 Watchdog установите лишь **новые** unit-файлы. Сначала обновите установленный код до этого коммита и проверьте, что прежний `--watchdog-once` работает. Если `git status --short` показывает отслеживаемые изменения, остановитесь и разберите их до `pull`. Существующие `okx-watchdog.service`/`.timer`, `.env`, SQLite и другие службы не перезаписывайте. Права существующего `.env` должны оставаться `0600`, владелец `okx-watchdog`; секреты не передавайте в аргументах команд. Новую службу эти команды ещё не включают:

```bash
sudo git -C /opt/okx-watchdog status --short
sudo git -C /opt/okx-watchdog pull --ff-only origin main
cd /opt/okx-watchdog/okx-trading-bot
./.venv/bin/python -m unittest discover -s tests -q
sudo test ! -e /etc/systemd/system/okx-health.service
sudo test ! -e /etc/systemd/system/okx-health.timer
sudo install -o root -g root -m 644 deploy/systemd/okx-health.service /etc/systemd/system/okx-health.service
sudo install -o root -g root -m 644 deploy/systemd/okx-health.timer /etc/systemd/system/okx-health.timer
sudo systemd-analyze verify /etc/systemd/system/okx-health.service /etc/systemd/system/okx-health.timer
sudo systemctl daemon-reload
sudo systemctl start okx-health.service
sudo journalctl -u okx-health.service -n 30 --no-pager
```

`systemctl start` может вернуть ошибку при `STALE`/`API_UNAVAILABLE`/`UNKNOWN`; посмотрите причину в журнале и проверьте системное UTC-время. Когда результат понятен, **явно** включите только новый таймер:

```bash
sudo systemctl enable --now okx-health.timer
systemctl list-timers --all okx-health.timer
```

Новый таймер запускается раз в пять минут, на две минуты позже Watchdog, под тем же непривилегированным пользователем. Service ограничивает запись файлов, память, CPU, время и объём сообщений в journal. Установка файлов сама по себе не включает таймер. Для отката отключите **только** новый таймер и удалите **только** новые unit-файлы; `health.sqlite3` сохраните для разбора истории:

```bash
sudo systemctl disable --now okx-health.timer
sudo rm /etc/systemd/system/okx-health.timer /etc/systemd/system/okx-health.service
sudo systemctl daemon-reload
```

Монитор на **том же сервере** не сможет сообщить о полном отключении сервера или интернета. Для этого нужен внешний наблюдатель с отдельным каналом связи. При сетевом сбое Telegram тоже может не доставить сообщение; после восстановления проверяйте systemd journal.

## Подготовка первой защищённой Demo-сделки (этап 4B.2B-2I)

`--first-demo-trade` — **однократная проверка перед первой сделкой**, а не команда исполнения. Она повторно использует локальный Demo GET-клиент, 100 закрытых BTC-USDT 15m свечей, EMA 9/21, сверку виртуального бюджета 5 000 USDT, неизменённый Risk Manager и `--order-preview`. Она читает журнал исполнителя только для проверки `HALTED` и прежних намерений. Этапы BUY, фактических fills, SL/TP, сопровождения, SELL и подтверждённого PnL в отчёте остаются неисполненными. Имеющийся внешний 1 BTC не считается позицией стратегии и не может быть продан. Фраза `REVIEW FIRST OKX DEMO BTC-USDT TRADE` подтверждает только **ручной просмотр** отчёта; она никогда не разблокирует торговый POST. Даже при BUY и `READY` итог всегда `BLOCK` и код выхода `1`.

Отдельная офлайн-симуляция `--protection-simulate` теперь содержит полный **учебный** BUY → OCO → TP → закрытие → PnL. События и комиссии хранятся в временной SQLite и восстанавливаются после перезапуска симулятора; повторный ID не дублирует сделку. При тайм-ауте, обрыве, частичном защитном SELL, расхождении Algo ID/объёма или двойной продаже PnL не объявляется подтверждённым. Это не журнал реальных исполнений OKX и не доказательство атомарной защиты.

Проверка на Windows из `okx-trading-bot`:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -q
.\.venv\Scripts\python.exe main.py --first-demo-trade
.\.venv\Scripts\python.exe main.py --first-demo-trade --first-demo-confirm "REVIEW FIRST OKX DEMO BTC-USDT TRADE"
.\.venv\Scripts\python.exe main.py --protection-simulate
```

Для существующего Ubuntu Watchdog обновите код только после проверки чистоты его Git-копии. **Не копируйте** рабочую SQLite или `.env` Windows на сервер, не меняйте Read-only API-права и не трогайте действующие Watchdog/Health units. Запустите только офлайн-тесты и однократную заблокированную проверку:

```bash
sudo git -C /opt/okx-watchdog status --short
sudo git -C /opt/okx-watchdog pull --ff-only origin main
cd /opt/okx-watchdog/okx-trading-bot
./.venv/bin/python -m unittest discover -s tests -q
sudo -u okx-watchdog ./.venv/bin/python main.py --first-demo-trade

```

Если Git показывает отслеживаемые изменения, остановитесь до `pull`. На Watchdog-сервере ожидается `BLOCK`: там нет подтверждённого стратегического журнала Windows и используется отдельный Read-only Demo-ключ. Код выхода `1` у проверок и симуляции означает **запрет исполнения**, а не требование «исправить» блокировку. Никакие новые службы или таймеры для торговли на Ubuntu в этом этапе не устанавливаются. Для реальной первой Demo-сделки потребуются отдельный согласованный контур владения BTC/PnL на сервере и подтверждённая схема attached SL/TP для **каждого** частичного fill в регионе этого аккаунта. Сейчас неизвестно, возможно ли обеспечить SL без временного незащищённого BTC, как доказать связь и взаимоисключение биржевых Algo-ног и как безопасно обработать округление BTC после комиссии. До подтверждения этих условий и отдельного разрешения на следующий этап торговые POST отсутствуют; `HALTED` не снимается.

## Диагностика блокировки первой Demo-сделки (этап 4B.2B-2J)

`--execution-diagnose` **только читает** существующий торговый `data/dry_run_journal.sqlite3`. Команда не требует `.env`, не обращается к OKX или Telegram, не меняет риск, бюджет, `HALTED` и намерения. На Windows из папки `okx-trading-bot`:

```powershell
.\.venv\Scripts\python.exe main.py --execution-diagnose
```

На Ubuntu из той же папки проекта:

```bash
./.venv/bin/python main.py --execution-diagnose
```

В отчёте **SQLite: BLOCKED** означает сохранённый `HALTED` или любое прежнее намерение: `--first-demo-trade` специально останавливается даже при ранее отклонённом намерении. Выводятся сохранённый код причины и UTC-время аварийной остановки, последнее намерение, его состояние, время свечи, создания и обновления, локально учтённый fill и признаки неопределённого BUY. **SQLite: CLEAR** означает только отсутствие локальной блокировки; **UNKNOWN** означает, что файл, схема или данные не прошли безопасную проверку. Неизвестный/повреждённый текст причины из базы не печатается: его нужно сверять вручную. Отдельная строка **Защита частичных BUY: UNVERIFIED** перечисляет недостающие доказательства по каждому fill, Algo ID, размеру и связи SL/TP, атомарности и взаимоисключению. Поэтому даже при `SQLite: CLEAR` общий результат остаётся `BLOCK` с кодом выхода `1`. Никакой из этих статусов не даёт права на отправку ордера.

Если команда показывает `HALTED`, не удаляйте файл, намерения или строки вручную. Сверьте конкретный `clientOrderId`, фактические fills и комиссии, SL/TP Algo ID и виртуальный BTC на OKX Demo с владельцем стратегии. Эта команда лишь объясняет блокировку; процедуры снятия `HALTED` в CLI нет. При запуске на Watchdog-сервере не копируйте туда рабочую торговую SQLite Windows: отсутствие локальной торговой базы даст `UNKNOWN`, что ожидаемо для отдельного сервера наблюдения. Watchdog, Health Monitor и их systemd-таймеры не меняются.

## Новая торговая SQLite на Ubuntu (этап 4B.2B-2J)

Эти команды предназначены **только для новой базы** `data/dry_run_journal.sqlite3` на отдельном Ubuntu-сервере. `--sqlite-prepare` только читает путь, права каталога, схему, прошлые намерения, `HALTED`, бюджет и состояние Risk Manager. Если файла нет, команда выдаёт токен текущего пятиминутного окна UTC. `--sqlite-init` требует точную фразу и этот токен, ещё раз проверяет состояние, строит журнал существующим `DecisionJournal` во временном файле с правами `0600` и публикует его атомарно без перезаписи существующего файла. Создаётся одна служебная запись `BLOCK`, **не торговое намерение**. Существующая, повреждённая или аварийная SQLite никогда не заменяется. Если после сбоя остался `.sqlite-bootstrap-*.sqlite3`, новая попытка блокируется до ручной проверки; не удаляйте его вслепую.

На Ubuntu проверьте чистоту локального Git и выполните обновление только если нет отслеживаемых изменений. Из `/opt/okx-watchdog/repo/okx-trading-bot`:

```bash
cd /opt/okx-watchdog/repo/okx-trading-bot
git status --short
git pull --ff-only origin main
./.venv/bin/python -m unittest discover -s tests -q
stat -c '%U:%G %a %n' data
sudo -u okx-watchdog ./.venv/bin/python main.py --sqlite-prepare
```

Если `data` не доступна пользователю `okx-watchdog` для записи и **в ней действительно только `.gitkeep`**, вручную выдайте этому пользователю права **только на каталог `data`**, затем повторите `--sqlite-prepare`:

```bash
sudo chown okx-watchdog:okx-watchdog /opt/okx-watchdog/repo/okx-trading-bot/data
sudo chmod 700 /opt/okx-watchdog/repo/okx-trading-bot/data
sudo -u okx-watchdog ./.venv/bin/python main.py --sqlite-prepare
```

Если статус `MISSING`, число намерений `0`, `HALTED: нет`, бюджет `UNCONFIRMED` и Risk Manager `UNINITIALIZED`, скопируйте **токен именно из этого вывода** и вручную выполните:

```bash
sudo -u okx-watchdog ./.venv/bin/python main.py --sqlite-init "INITIALIZE NEW OKX DEMO SQLITE" --sqlite-token ВАШ_ТОКЕН
sudo -u okx-watchdog ./.venv/bin/python main.py --sqlite-prepare
sudo -u okx-watchdog ./.venv/bin/python main.py --execution-diagnose
```

После создания SQLite бюджет по-прежнему `UNCONFIRMED`, дневная база Risk Manager не задана. Если хотите **отдельно** подтвердить 5 000 виртуальных USDT, используйте существующий Demo Read-only механизм: сначала проверьте виртуальный USDT, внешний 1 BTC, комиссию и ограничения в `--budget-preview`, затем вручную используйте **новый токен именно из этого просмотра**:

```bash
sudo -u okx-watchdog ./.venv/bin/python main.py --budget-preview
sudo -u okx-watchdog ./.venv/bin/python main.py --confirm-budget "CONFIRM DEMO BTC-USDT 5000 USDT" --budget-token ВАШ_НОВЫЙ_ТОКЕН_БЮДЖЕТА
```

Токен SQLite к бюджету не подходит. Внешний BTC не включается в капитал стратегии. При неизвестных балансах, правах API или старом состоянии Risk Manager подтверждение блокируется.

Ни одна из этих команд не отправляет торговый POST, не создаёт BUY/SELL и не снимает `HALTED`. `--execution-diagnose` может вывести `SQLite: CLEAR`, но защита каждой частично исполненной покупки остаётся **UNVERIFIED**, первая Demo-сделка остаётся `BLOCK`. Команды не меняют Watchdog, Health Monitor или их systemd timers. Не копируйте рабочую SQLite Windows и не запускайте инициализацию от root.

## Офлайн-исследование роста стратегии (этап 4B.2B-2K)

`--growth-research` сравнивает неизменённую EMA 9/21 с четырьмя заранее заданными вариантами: фильтром тренда (цена выше растущей EMA50), волатильности (ATR14/цена от 0,15% до 3%), силы пересечения (разница EMA9−EMA21 не меньше 0,1 ATR14) и всеми фильтрами вместе. Пороги фиксированы в коде до проверки финального периода. Нужен **локальный исторический CSV**, который вы получили из надёжного источника и проверили; команда сама не скачивает данные и не обращается к OKX.

Поместите файл в `data/`, чтобы он не попал в Git. Заголовок строго `opened_at,open,high,low,close,confirm`; пример одной строки: `2024-01-01T00:00:00Z,42000,42100,41900,42050,1`. Все строки должны быть подтверждёнными 15-минутными свечами BTC-USDT SPOT в непрерывном порядке от старой к новой, с UTC-временем. Открытые свечи, пропуски и противоречивые OHLC отклоняются. Для выводов потребуется существенно больше 100 свечей — желательно месяцы разных рыночных режимов.

Из `okx-trading-bot` запустите, подставив **проверенные для вашего Demo BTC-USDT SPOT** `minSz`, `lotSz`, `tickSz`, `maxMktSz`, ставку taker и собственную оценку проскальзывания:

```bash
./.venv/bin/python main.py --growth-research data/btc_usdt_15m.csv \
  --research-min-sz MIN_SZ --research-lot-sz LOT_SZ \
  --research-tick-sz TICK_SZ --research-max-mkt-sz MAX_MKT_SZ \
  --research-taker-fee FEE_RATE --research-slippage SLIPPAGE_RATE
```

Для Windows PowerShell используйте те же аргументы в одной строке с `.\.venv\Scripts\python.exe main.py`. `--research-taker-fee` задаёт положительную долю расхода; альтернативно `--research-okx-taker-rate=-0.001` принимает подписанную ставку OKX и превращает отрицательное списание в положительную стоимость модели `0.001`. Положительная подписанная ставка (возможный rebate) блокируется: модель rebates не поддерживает. Эти два аргумента нельзя использовать одновременно. Все суммы в отчёте — модельные виртуальные USDT, не реальный баланс Demo. Внешний 1 BTC не включается в капитал модели.

Каждый сигнал формируется только после закрытия свечи и исполняется **не раньше открытия следующей**. Модель учитывает taker-комиссию при входе и выходе, проскальзывание, `minSz`/`lotSz`/`tickSz`/`maxMktSz`, округление BTC вниз, SL 1%, TP 2%, максимум одну позицию и пять входов за UTC-сутки. Размер рассчитывается из риска 0,5% текущего модельного капитала, дневного предела потерь 2%, доступных USDT и двух ограничителей позиции: максимум 50% капитала и абсолютный предел 5 000 USDT. Прибыль реинвестируется в следующий модельный вход, пока не сработает предел. Дневная база фиксируется только внутри симуляции при смене UTC-даты; рабочий Risk Manager не вызывается и не меняется. Реализованные убытки не компенсируются прибылью при проверке дневного запрета. Если одна свеча касается и SL, и TP, для сделки принимается SL; при гэпе ниже стопа выход оценивается по худшей цене открытия. Это не доказывает возможность реального своевременного SL/TP в OKX Demo.

Данные делятся по времени на 60% `TRAIN`, 20% `VALIDATION`, 20% `FINAL_TEST`. Вариант выбирается только по первым двум частям: 40% оценки `(доходность − просадка)` обучения и 60% проверки. Финальный период используется один раз для выбранного варианта, без подгонки по нему. Для каждого варианта показаны доходность, максимальная просадка, profit factor закрытых сделок, число сделок и разница с Buy & Hold после сопоставимых taker-затрат. Незакрытая позиция в конце только оценивается по рынку; её результат не добавляется в profit factor. Buy & Hold — отдельный полностью инвестированный ориентир без ограничителя позиции стратегии.

Дополнительно отчёт проверяет двойную комиссию, тройное проскальзывание, синтетический гэп вниз на 10% после первого входа и серию десяти модельных стопов в одни UTC-сутки. Если нет хотя бы примерно шести месяцев истории, 50/20/20 закрытых сделок по трём периодам, определённого profit factor либо финальный период не подтверждает превосходство после затрат, выводится **«нет достаточных оснований»** и предупреждение. Даже исследовательский кандидат не разрешает торговлю. У исторических свечей нет сведений об очереди исполнения, реальной ликвидности, задержке Algo ID и атомарной защите частичных BUY; `HALTED` и запрет торговых POST остаются без изменений.

## Исторические свечи OKX и Growth Research (этап 4B.2B-2L)

`--download-history` использует только публичный `GET /api/v5/market/history-candles` для BTC-USDT SPOT, `bar=15m`, до 100 свечей на страницу. Региональный REST-домен берётся из существующего `OKX_REGION` (`global`, `eea`, `us`); при ошибке домен не заменяется. API-ключи для этой команды не требуются. Между страницами есть пауза 0,11 с, временные сетевые ошибки и лимит OKX повторяются ограниченно существующим публичным клиентом. Курсор движется только к более старым свечам; дубли, пропуски, неправильный порядок, UTC-время, OHLC, три поля объёма и `confirm` проверяются. Текущая незакрытая свеча исключается. При ошибке ряд не публикуется.

Из папки `/opt/okx-watchdog/repo/okx-trading-bot` на Ubuntu 24.04:

```bash
cd /opt/okx-watchdog/repo/okx-trading-bot

  --research-min-sz MIN_SZ --research-lot-sz LOT_SZ \
  --research-tick-sz TICK_SZ --research-max-mkt-sz MAX_MKT_SZ
```

Замените плейсхолдеры актуальными `minSz`, `lotSz`, `tickSz` и `maxMktSz` из публичного `GET /api/v5/public/instruments` (их показывает `--reconcile`, если безопасная Demo-сверка доступна). Исследование без ставки и проскальзывания печатает три **условных** сценария затрат (0,05%/0,05%; 0,1%/0,1%; 0,2%/0,3%) и явное предупреждение: это не подтверждённые тарифы или фактическое проскальзывание. Если ставка вашего Demo-счёта подтверждена отдельно, укажите `--research-okx-taker-rate` или `--research-taker-fee` вместе с `--research-slippage`; историческая ставка за весь период и проскальзывание всё равно остаются допущениями. Ни один вариант не снимает блокировку торговли.

По умолчанию скачиваются 17 280 закрытых свечей (около 180 суток) в `data/btc_usdt_15m.csv`, который исключён из Git. CSV имеет требуемый `--growth-research` заголовок `opened_at,open,high,low,close,confirm`; объёмы проверяются при загрузке, но не используются стратегией и в CSV не пишутся. Проверка сообщает размеры частей TRAIN/VALIDATION/FINAL_TEST (60/20/20) и требует минимум 8 640/2 880/2 880 свечей соответственно. Если доступная история OKX короче, непрерывная часть сохраняется с пометкой `НЕДОСТАТОЧНО` и кодом выхода `1`; вывод исследования на такой выборке не даёт достаточных оснований. При менее чем 100 валидных свечах CSV не создаётся. `--history-bars N` меняет число свечей в пределах 100–35 040, например для проверки небольшого окна: `./.venv/bin/python main.py --download-history --history-bars 100 --history-output data/check_100.csv`. Уже существующий файл **не перезаписывается** и даже запросы к API не начинаются. Для осознанного обновления готового CSV добавьте `--overwrite-history`; замена произойдёт лишь после проверки и полной записи нового временного файла.

Ни загрузка, ни исследование не читают торговую SQLite, не меняют бюджет 5 000 Demo USDT, Risk Manager, `HALTED`, Watchdog, Health Monitor или systemd units. Торговые POST/BUY/SELL отсутствуют. В облачном окружении с ограниченным доступом к `okx.com` живую загрузку следует выполнять на вашей Ubuntu; офлайн-тесты используют подменённые ответы.

## Первый отчёт Growth Research: сверка единиц и комиссии (этап 4B.2B-2M)

Для подтверждённых на Demo BTC-USDT SPOT значений `minSz=0.00001 BTC`, `lotSz=0.00000001 BTC`, `tickSz=0.1 USDT`, `maxMktSz=1000000`, `maker=-0.0008`, `taker=-0.001` используйте на Ubuntu из каталога `okx-trading-bot`:

```bash
./.venv/bin/python main.py --growth-research data/btc_usdt_15m.csv \
  --research-min-sz 0.00001 --research-lot-sz 0.00000001 \
  --research-tick-sz 0.1 --research-max-mkt-sz 1000000 \
  --research-okx-taker-rate=-0.001 --research-slippage 0.002
```

Подписанная taker-ставка OKX `-0.001` означает **списание 0,1%**; в модели оно преобразуется в расход `+0.001` при входе и выходе. Maker `-0.0008` не применяется к моделируемым рыночным исполнениям. Модель считает эквивалент расходов в USDT; фактическая валюта удержания комиссии без исполненного ордера не подтверждена. `0.002` проскальзывания (0,2% на каждую сторону) — **консервативное сценарное допущение**, не измерение OKX. Отчёт дополнительно показывает стресс для двойной taker-комиссии (`0.002`), тройного проскальзывания (`0.006`), гэпа и серии стопов. Текущая ставка Demo не доказывает, что та же ставка действовала на протяжении всех исторических свечей.

Бэктест моделирует рыночный **BUY** следующей открытой свечи. `maxMktSz` для этого сценария трактуется как предел стоимости ордера в котируемой валюте USDT: количество BTC ограничивается `maxMktSz / модельная цена входа` с округлением вниз по `lotSz`. Его нельзя сравнивать напрямую с `minSz` в BTC. Обзор [CCXT OKX parseMarket](https://github.com/ccxt/ccxt/blob/master/ts/src/okx.ts) также отображает `maxMktSz` для SPOT в `limits.cost.max`; в этой облачной среде прямой доступ к официальному тексту [OKX API V5](https://www.okx.com/docs-v5/en/) закрыт сетевой политикой, поэтому перед использованием отчёта как подтверждения биржевого ограничения проверьте актуальное описание поля для своего региона. При 1 000 000 USDT это ограничение не срабатывает для стратегии, где отдельная покупка уже ограничена 50% модельного капитала и 5 000 USDT. Исследование читает только CSV и не открывает торговую SQLite; его результаты не разрешают сделки и не снимают `HALTED`.

## Диагностика блокировок Demo перед первой сделкой (этап 4B.2B-2N)

На Ubuntu из `/opt/okx-watchdog/repo/okx-trading-bot` после обычного `git pull --ff-only origin main` и офлайн-тестов запустите **только чтение**:

```bash
./.venv/bin/python main.py --market-diagnose
./.venv/bin/python main.py --budget-preview
./.venv/bin/python main.py --reconcile
./.venv/bin/python main.py --protection-capabilities
```

`--market-diagnose` использует только публичные GET инструмента и тикера; не требует Demo-ключей, не использует торговую SQLite и не запрашивает свечи. `--budget-preview` и `--reconcile` тоже больше не требуют 100 свечей для проверки бюджета: они читают публичные инструмент/тикер отдельно от приватных **Demo GET**. Это устраняет ложную общую ошибку цены, когда раньше сбой запроса свечей скрывал исправные цену и ограничения. Диагностика теперь разделяет `PRICE` (положительный `ticker.last`), `QUOTE_TIME` (`ticker.ts` в UTC и не старше 60 секунд), `INSTRUMENT` (именно live BTC-USDT SPOT и валюты BTC/USDT), `LIMITS` (`minSz`, `lotSz`, `tickSz`, `maxLmtSz`, `maxMktSz`), `FEES` (подписанные maker/taker), `JOURNAL`, `RISK_SETTINGS` и `RISK_STATE`. Отсутствующий до подтверждения бюджета дневной Risk Manager показывается как `UNINITIALIZED`; он **не создаётся** диагностикой. Устаревший тикер, пустое поле ограничения, ошибка Demo API или неизвестное состояние оставляют `BLOCKED`. Ошибки транспорта выводятся без текста ответа и секретов. Код выхода `1` ожидаем для заблокированного этапа; не пытайтесь «исправить» его удалением SQLite или изменением `HALTED`.

Точный сбой вашего Ubuntu-сервера можно назвать только по выводу этих команд: в облачной копии нет его ответов OKX и рабочей SQLite. Даже если рыночные проверки станут `OK`, отсутствие отдельно подтверждённого бюджета 5 000 виртуальных USDT и дневной базы Risk Manager сохраняет `--reconcile=BLOCKED`. `--budget-preview` лишь предлагает одноразовый токен, когда **вся** сверка чистого старта пройдена; эта версия не подтверждает бюджет автоматически. Внешний 1 BTC не входит в капитал стратегии и не разрешён к продаже.

### Доказательства и план эмпирической проверки attached TP/SL

| Уровень | Что известно | Что остаётся недоказанным |
| --- | --- | --- |
| Интерфейс | [Официальный Python SDK OKX](https://github.com/okxapi/python-okx/blob/master/okx/Trade.py) содержит параметр `attachAlgoOrds`; SDK и API V5 описывают GET для ордера, fills и Algo. | Приём и фактическое создание защитных ордеров именно в BTC-USDT SPOT Demo вашего региона. |
| Наблюдение | Demo GET может вернуть лимиты, ставки, открытые ордера, fills и Algo-списки; текущая диагностика не видела собственного BUY. | Связь Algo ID с `clOrdId`/`ordId`, скорость появления SL после каждого частичного fill и статус остатка BUY. |
| Модель | Офлайн-тесты считают купленным ботом только net BTC после комиссий и блокируют неизвестный SL, повтор, таймаут и чужой 1 BTC. | Реальная валюта комиссии, точный объём SL/TP, взаимоисключение ног, недопущение двойной продажи и подтверждённый PnL после закрытия. |

Отдельный **будущий** эксперимент возможен только после нового явного решения владельца и разработки отдельного контролируемого режима; в этом этапе торговых POST и Trade-разрешений нет. Перед тем экспериментом владелец должен вручную проверить чистый Demo-счёт, отдельный бюджет/дневной риск, отсутствие прежних намерений и `HALTED`, лимиты и план реагирования на незащищённый BTC. Даже минимальный тест может временно оставить виртуальный BTC без защиты; это отдельный риск, который нужно оценить до разрешения теста. Минимальный Demo BUY с attached TP/SL должен быть связан с заранее сохранённым уникальным `clOrdId`; после него независимые GET должны подтвердить каждый `tradeId`, размер и валюту комиссии, net BTC бота, идентификаторы Algo (в том числе возможный общий OCO ID), действующий SL на весь net BTC, привязку защитных ног к BUY и их взаимоисключение. Для активного частичного BUY необходимо доказать защиту **каждой новой порции** до разрешения следующего входа; при задержке ID, отказе SL, таймауте или расхождении сохраняется `HALTED`. Отмена остатка, срабатывание защитной ноги и закрытие проверяются отдельной сверкой fills, баланса и PnL без продажи внешнего BTC. Наблюдение GET после одного ордера не доказывает атомарную защиту будущих частичных исполнений; до эмпирического подтверждения всех условий статус защиты остаётся `UNVERIFIED`, торговля `BLOCK`.

Никакие Watchdog, Health Monitor, systemd units, бюджет, дневные лимиты и рабочая SQLite этим изменением не модифицируются; команды диагностики только читают. `--protection-capabilities` по-прежнему всегда возвращает `BLOCK`.

## Demo-трейдер: реальные сделки на виртуальном счёте (этап 5)

`--demo-trade-once` — первый режим, который **отправляет ордера**, и только на OKX Demo (заголовок `x-simulated-trading: 1`; `Config` по-прежнему запрещает LIVE). Один запуск = один цикл:

1. Если сохранена аварийная остановка `HALTED` — ничего не делает.
2. Сверяет отслеживаемую позицию с биржей: сработал ли OCO (тейк/стоп), завершились ли ордера, прерванные сбоем.
3. Считает EMA 9/21 на последней закрытой 15m свече; каждая свеча обрабатывается **один раз**, сигнал старше 20 минут игнорируется.
4. **BUY** (если позиции нет): рыночная покупка, размер — риск 0,5% капитала стратегии при стопе 1% с учётом taker-комиссии и проскальзывания; не больше капитала стратегии и 98% свободных USDT. После исполнения на **фактически купленный** BTC (за вычетом комиссии, округлённо вниз по `lotSz`) ставится биржевой **OCO**: SL −1%, TP +2% от средней цены. Если OCO не встал — BTC сразу продаётся по рынку и включается `HALTED`.
5. **SELL** (если позиция есть): снимается OCO и продаётся ровно купленный ботом объём. Остальной BTC на Demo-счёте бот не трогает.

Ограничения: одна позиция, максимум 5 входов за сутки UTC, дневной реализованный убыток не больше 2% капитала на начало суток. Капитал стратегии = `OKX_TRADER_BUDGET_USDT` (по умолчанию 5 000) + накопленный PnL закрытых сделок. Таймаут или неоднозначный ответ на торговый POST никогда не повторяется вслепую: включается `HALTED`, следующий запуск после снятия остановки находит ордер по `clOrdId`. Журнал — отдельная SQLite (`OKX_TRADER_STATE_PATH`); старые SQLite проекта не используются. О каждой сделке и остановке приходит сообщение в Telegram (если настроен).

Команды:

```bash
./.venv/bin/python main.py --demo-trade-status          # журнал, позиция, PnL; без запросов к OKX
./.venv/bin/python main.py --demo-trade-once            # один цикл
./.venv/bin/python main.py --demo-trade-resume "RESUME OKX DEMO TRADER"     # снять HALTED после ручной проверки
./.venv/bin/python main.py --demo-trade-abandon "ABANDON OKX DEMO POSITION" # позиция закрыта вручную на OKX
```

### Установка на Ubuntu

1. Ключ: если `OKX_DEMO_TRADE_API_KEY/SECRET/PASSPHRASE` не заданы, трейдер использует уже прописанный `OKX_DEMO_API_KEY/OKX_DEMO_API_SECRET/OKX_DEMO_PASSPHRASE` — у этого Demo-ключа должно быть право **Trade**. Отдельный торговый ключ можно задать переменными `OKX_DEMO_TRADE_*`.
2. Добавьте в `.env` сервера (`sudoedit`, права 600):

   ```
   OKX_TRADER_ENABLED=1
   OKX_TRADER_STATE_PATH=/var/lib/okx-watchdog/demo_trader.sqlite3
   ```

3. Проверьте путь кода: unit-файл использует `/opt/okx-watchdog/repo/okx-trading-bot`. Если код лежит в другом месте, исправьте `WorkingDirectory`/`ExecStart` перед установкой.
4. Тесты, пробный цикл, затем таймер (каждые 5 минут; сделки — не чаще одной на свечу):

   ```bash
   cd /opt/okx-watchdog/repo/okx-trading-bot
   git pull --ff-only origin main
   ./.venv/bin/python -m unittest discover -s tests -q
   sudo -u okx-watchdog ./.venv/bin/python main.py --demo-trade-once
   sudo install -o root -g root -m 644 deploy/systemd/okx-demo-trader.service /etc/systemd/system/
   sudo install -o root -g root -m 644 deploy/systemd/okx-demo-trader.timer /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable --now okx-demo-trader.timer
   journalctl -u okx-demo-trader.service -n 50 --no-pager
   ```

Остановить торговлю: `sudo systemctl disable --now okx-demo-trader.timer` (открытая позиция остаётся под биржевым OCO) или `OKX_TRADER_ENABLED=0`. Watchdog будет отмечать сделки бота как изменения баланса/ордеров (`SUSPICIOUS`) — это ожидаемо.

**Важно:** офлайн-исследование (этап 4B.2B-2K…2M) показало, что EMA 9/21 на 15m за последние 180 дней убыточна (profit factor 0,3 с комиссией 0,1%). Demo-трейдер нужен для отладки исполнения, а не для заработка. Реальный счёт этим режимом не поддерживается.

## Дневной трендовый бот на Demo (этап 5.1)

`--trend-once` — второй Demo-бот, проверяющий стратегию-кандидата для реального счёта. Раз в сутки UTC (после закрытия дневной свечи `1Dutc`) он считает, на скольких из периодов 20/30/40/50/60 дней последняя цена выше цены N дней назад, и держит такую же долю своей книги в BTC: 0%, 20%, …, 100%. Остальное — USDT. Сделка выполняется, только если доля отличается от цели хотя бы на 10 п.п. Стоп-лосса нет: выход только при ежедневной переоценке.

Книга бота виртуальная и отдельная: `OKX_TREND_BUDGET_USDT` (по умолчанию 100, как реальный счёт), учёт BTC/USDT и комиссий — в `OKX_TREND_STATE_PATH`. Другие балансы Demo не трогаются. Неопределённый ответ на ордер → `HALTED`, восстановление по `clOrdId` после `--trend-resume "RESUME OKX DEMO TREND"`.

Офлайн-исследование на дневных свечах OKX 2018–2026 (затраты 0,15% на сторону): за весь период ×1,16–1,75 BTC относительно удержания в зависимости от набора периодов, максимальная просадка ~50% против 76% у удержания. В сильно растущие годы (2023, 2024) стратегия **отстаёт** от удержания (×0,84 и ×0,67 BTC). Это защита от длительных падений, а не гарантированный рост.

```bash
./.venv/bin/python main.py --trend-status
./.venv/bin/python main.py --trend-once
sudo install -o root -g root -m 644 deploy/systemd/okx-demo-trend.service deploy/systemd/okx-demo-trend.timer /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now okx-demo-trend.timer
```

В `.env`: `OKX_TREND_ENABLED=1`, `OKX_TREND_STATE_PATH=/var/lib/okx-watchdog/trend_trader.sqlite3`.
